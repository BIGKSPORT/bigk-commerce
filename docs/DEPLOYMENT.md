# Deployment and launch gate

No live deployment has been performed. The supplied application is for local review first.

## Infrastructure

Use a Node.js 24 host with a single instance and a persistent local disk mounted at the database directory. Terminate HTTPS at a trusted reverse proxy; restrict origin access and set the canonical `APP_URL` to the public HTTPS origin. Do not trust arbitrary forwarded headers. Configure secrets in the hosting provider's secret manager, not in the source archive.

Use a non-root process. Restrict the database and backup directories to the application operator. Do not use a static-only host or an ephemeral serverless filesystem for this implementation. If using Docker, mount `/app/data` persistently. The Dockerfile is supplied but has not been built or run in this session.

For larger deployments, complete the PostgreSQL/distributed-job migration described in ARCHITECTURE.md before adding instances.

## Required configuration

- `APP_URL`: exact canonical origin, HTTPS for live mode.
- `DATABASE_PATH`: persistent database file path.
- `RECEIPT_SECRET`: cryptographically random value, at least 32 characters. Rotating it invalidates the ability to regenerate private links for retried checkouts; existing hashed receipts remain verifiable.
- `ADMIN_PASSWORD_HASH`: generated by `npm run admin:password`. Use a unique password of at least 16 characters.
- `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`: server-only; use Stripe test mode first.
- `RESEND_API_KEY` and `EMAIL_FROM`: verified sending domain and sender. Configure SPF, DKIM and DMARC through your provider.
- `COMMERCE_MODE=demo` and `LIVE_COMMERCE_APPROVED=false` during review.

Before switching modes, require strong credentials, legal approval, configured email, tax registrations, verified stock and the checks below. Live checkout has a technical gate requiring live mode, the explicit approval flag, HTTPS origin, payment configuration and a receipt signing secret of at least 32 characters. These values do not prove business readiness.

## Stripe setup

1. Configure supported EUR payments and approved European markets. The adapter uses hosted Checkout, inclusive prices, automatic tax and a general tangible-goods tax code. Validate actual apparel tax categories, VAT registrations and shipping tax treatment with your tax adviser and Stripe configuration before use.
2. Register `/api/webhooks/stripe` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired` and `checkout.session.async_payment_failed`.
3. Keep sandbox and live databases/keys isolated. Complete real Stripe sandbox checkout with success, failure, cancellation, delayed payment, duplicate events, signature rejection and refunds. No live payment has been made during development.
4. Monitor `payment_review` orders. A late asynchronous success may need manual stock allocation or refund. The store intentionally does not fulfill it automatically.
5. Final delivery information confirmed in Stripe is copied from the signed paid event into the admin order. Verify it against the provider before dispatching.

## Jobs, monitoring and backups

Schedule `inventory:expire` and `email:deliver` every minute, supplying environment variables. Protect scheduler access; the jobs are local scripts rather than unauthenticated HTTP cron endpoints. The build emits dependency-bundled tasks at `.next/jobs/expire-reservations.mjs` and `.next/jobs/deliver-emails.mjs`. In the supplied Docker image, these are `jobs/expire-reservations.mjs` and `jobs/deliver-emails.mjs`; run them with Node in the same environment and persistent volume as the application.

Alert on webhook failures, old pending orders, `payment_review`, unsuccessful email jobs, login spikes and disk capacity. Do not log credentials, payment details, contact details or receipt bearer tokens. Outbox jobs lease for 60 seconds and retry up to ten times with backoff; alert on exhausted attempts. Provider idempotency has a finite retention period, so investigate ambiguous long outages rather than repeatedly resetting jobs.

Use SQLite's online backup facility or a consistent snapshot procedure; copying just the database file while WAL writes are active is unsafe. Encrypt backups, restrict access and rehearse restore into an isolated environment. Set and implement a legally reviewed retention and deletion policy.

## Final acceptance

- Verify all SKU prices, variant sizes/colours, images and physical counts. Do not activate products with shared or uncertain colour photography.
- Add verified material/care specifications and size measurements.
- Replace development legal notices with approved company, privacy, terms, returns and support information. Current placeholder policies are not fit for live sales.
- Validate actual delivery rates, time promises and carrier coverage.
- Complete email domain verification and test sign-in, expired links, confirmations and tracking messages.
- Complete browser purchase tests, mobile/keyboard/screen-reader review, access-control testing and concurrent last-unit purchase tests against production-like infrastructure.
- Complete hosted backups/restore tests, monitoring, rate limiting and an independent security review.
- Only then enable `COMMERCE_MODE=live` and `LIVE_COMMERCE_APPROVED=true` and approve the individual catalogue items.

The website can be tailored to outperform a generic storefront for BigK's customers. Superiority over Shopify as a complete commerce platform has not been established or claimed.
